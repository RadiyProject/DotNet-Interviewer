# Практика написания тестов

В разделе **«Тестирование» → «Практика»** добавлены C48–C51. Их также можно найти в общей практике по теме Testing. Порядок: C37 → C50 → C49 → C48 → C51.

| ID | Что пишет пользователь | Что проверяется | Минуты |
|---|---|---|---:|
| C48 | NUnit-проверки HTTP-функции через FakeHandler | Retry budget, ошибки, заранее отменённый token, тело ответа и владение клиентом | 35 |
| C49 | NUnit-проверки TTL-store с ManualClock | Строгая граница срока, absolute/sliding, независимость ключей и overwrite | 30 |
| C50 | Примеры и проверки свойств сортировки | Порядок, длина, кратность, неизменность входа, крайние int и empty | 30 |
| C51 | Интеграционные NUnit-проверки реального SQLite | Happy path, rollback при CHECK/UNIQUE, ledger и lifecycle соединения | 40 |

## Механизм проверки

Пользователь реализует `Kata.Verify(...)`, используя NUnit. Harness вызывает её с корректной реализацией и затем с намеренно дефектными вариантами. Корректный код должен пройти весь набор написанных пользователем проверок; каждый дефект должен вызвать assertion failure или другую неожиданную ошибку. `NotImplementedException` за обнаружение дефекта не засчитывается.

Сначала идут положительные контроли. Если хотя бы одна корректная реализация отвергнута, баллы за обнаружение мутантов не выдаются. Это не позволяет получать высокую оценку за безусловное исключение. Пустой Verify тоже не получает полный результат: дефекты останутся незамеченными. В C50 есть три корректных варианта, включая допустимый reuse уже отсортированного массива; в C51 — два допустимых порядка debit/credit в общей транзакции.

Это ограниченная mutation-style self-practice. Полный результат означает различение предложенных вариантов, а не доказательство полноты тестов или защиту от намеренного обхода harness. Отдельный `dotnet test`, test discovery и атрибуты `[Test]` здесь не используются: исполняется тот же console-harness, что у остальных C# задач. Для переноса в рабочий проект сценарии оформляются отдельными тестами с обычным runner.

## Важные контракты

- **C48:** повторяется только 503, не произвольный 5xx/429; максимум три попытки, без backoff. Проверяется precancellation, а не вся in-flight cancellation семантика. Клиент принадлежит тесту. Новый response создаётся для каждого вызова handler.
- **C49:** ManualClock управляет `GetUtcNow`, но не запускает таймеры. Нет ожидания wall clock. При `now == deadline` значение уже отсутствует; чтение TTL не продлевает.
- **C50:** сравнивать только distinct-множества недостаточно — важны повторы. Snapshot входа делается до вызова. Новый reference не требуется контрактом.
- **C51:** схема и исходные данные создаются заново на каждом открытом `:memory:` соединении. Внешняя транзакция теста запрещена: она способна скрыть дефект проверяемого transfer. После ошибки проверяются обе таблицы, а не только исключение. Тесты SQLite не доказывают поведение PostgreSQL.

NUnit уже зафиксирован в manifest на **4.3.2**. В этой версии `Assert.ThrowsAsync` синхронный и возвращает исключение: его не нужно `await`. Документация по текущему NUnit 5 описывает другой API; при чтении смотрите раздел «NUnit 4 and earlier». Явный try/catch с последующим NUnit assertion также допустим.

## Зависимости и ограничения

Использованы уже разрешённые `NUnit` и `Microsoft.EntityFrameworkCore.Sqlite` (для транзитивного Microsoft.Data.Sqlite). Manifest, образы и runner не менялись, новые зависимости не устанавливались. При самостоятельной проверке тренажёр использует обычный existing restore/cache flow. Исходники задач и их English overlays имеют одинаковые API и код заготовок; названия результатов harness переведены.

Проведена статическая сверка JSON, ID, связанных карточек, packages/harness и переводов. Компиляция, запуск приложения и выполнение новых harness не проводились по инструкции пользователя; их нужно проверить в вашем окружении.
