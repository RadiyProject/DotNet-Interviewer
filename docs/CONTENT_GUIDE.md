# Как добавлять задания

`trainer/content/tasks.json` — массив объектов. Контент считается доверенным кодом репозитория. Не импортируй непроверенный task-pack из сети автоматически.

## Общие поля

- `id`: уникальная стабильная строка без HTML, например `C10`; изменение ID создаёт новую историю.
- `title`, `desc`, `cat`, `prio` (`P0/P1/P2`), `minutes`: положительное число минут.
- `engine`: `csharp`, `postgres`, `sqlite`, `quiz` или `review`.
- `kind`, `requirements[]`, `cases[]`, `starter`, `hints[]`, `review[]`.
- `related`: необязательный массив ID тематически связанных вопросов/задач. Укажи связь в обеих карточках для переходов туда и обратно. Тип раздела определяется по engine; список внутри раздела группируется по cat.
- `source`: `[название, https URL]`, `origin`: честное происхождение постановки.
- `answer`: объяснение, механизм решения, границы и типичные ошибки. Не ограничивайся правильной буквой.
- `tags`: стабильные ID доменов/навыков из `content/tags.json`, например `fintech`, `distributed-systems`, `testing`.

Для каждого задания добавляй английский текстовый overlay по тому же ID в `content/tasks.en.json`. Не меняй порядок choices, grading-поля или код заготовки; перевод комментариев допустим. Формат языковых файлов, словарей и тегов описан в [LOCALIZATION_AND_TAGS.md](LOCALIZATION_AND_TAGS.md).

В публичный каталог API не отправляются `answer`, `correct`, `reference`, `fixtures`, `harness`. Разбор открывается по отдельному действию с отметкой учебной попытки либо после завершения.

## Quiz

Добавь `choices` (массив вариантов). `correct` задаёт формат:

- `correct: 2` — одиночный выбор (radio), правильный индекс с нуля.
- `correct: [0, 2, 3]` — множественный выбор (checkbox), все правильные индексы с нуля. Используй минимум два разных верных варианта, без повторов и вне диапазона.

API отправляет клиенту только флаг `multiple`, не правильные индексы и не число верных вариантов. В запросе и черновике одиночный ответ остаётся строкой индекса (`"2"`), множественный хранится строкой JSON-массива (`"[0,2,3]"`). Старые одиночные вопросы, черновики и история совместимы.

Сервер сравнивает наборы: порядок не важен, но пропущенный правильный или выбранный неверный вариант означает 0/100. Для каждой отметки возвращается разбор: выбрана ли она и верна ли. Это не частичные баллы по числу совпадений. В условии явно укажи формат и правило полного совпадения. Смотри Q051–Q058.

Не задавай неоднозначные вопросы без контекста версии/провайдера. `starter` пустой, `review` пустой. Не подсказывай ответ в заголовке источника. Для вопроса о конкретной версии назови её явно.

## C#

Добавь `harness: "C10.cs"`; создай соответствующий файл в `trainer/harness`. Решение участника компилируется как `Solution.cs`, harness как `Program.cs`, target net10.0. Harness может использовать стандартную библиотеку и Microsoft.AspNetCore.App. Типы из starter принадлежат решению; не объявляй их второй раз в harness.

Последняя строка stdout должна содержать JSON-массив:

```json
[{"name":"Empty input","passed":true,"detail":""}]
```

Смотри T02.cs и T01.cs. Вызовы проверок изолируй try/catch, проверяй ошибки и cancellation. Для HTTP используй fake handler, не сеть. Не используй случайность без seed, wall-clock assertions с маленьким допуском или гонки, которые лишь «иногда» воспроизводятся. Для сложного concurrency лучше барьеры и контролируемые зависимости, чем один stress loop. Текущий C06 ограниченно проверяет concurrency: дополнительные детерминированные сценарии полезны.

Покрой пустой/единичный вход, повторяющиеся ключи, порядок, границы, overflow, исключения и владение ресурсами, если это относится к контракту. Сценарии не должны отражать только одну реализацию. Решение и harness находятся в одном процессе: это открытая self-practice проверка, её можно обойти намеренно.

## SQL

Добавь `reference` с эталонным SELECT и `fixtures`:

```json
[{"name":"Boundary dates","setup":"DROP TABLE IF EXISTS items; CREATE TABLE items(id INTEGER); INSERT INTO items VALUES(1);"}]
```

Каждый fixture заново создаёт таблицы. На нём сначала считается reference, потом выполняется решение. Проверяются значения, количество, порядок строк и столбцов; названия aliases не сравниваются. Значения нормализуются в строки. Поддержка decimal/NULL/date в новых заданиях требует учитывать конкретную сериализацию provider, а не предполагать универсальное равенство типов.

PostgreSQL поднимается заново внутри networkless контейнера. Используется psql, statement_timeout=2500ms. SQLite работает в памяти. Это два разных provider; пиши варианты для каждого там, где семантика отличается. Данные должны проверять ошибки, а не только happy path: совпадающие имена, NULL, пустые таблицы, ties, timestamps на границах. Текущие дата-задания используют ISO date TEXT и суммы INTEGER, это явно указано в контракте.

Песочница одноразовая; разрешение произвольного SQL не даёт доступ к прогрессу/host/network. Но роль PostgreSQL внутри неё широкая: не превращай этот механизм в публичный SQL сервис без переработки.

## Review / architecture

`engine: review`. `review[]` — ясные критерии, которые пользователь отмечает сам. Дай содержательный `answer`: хотя бы требования, один обоснованный дизайн, tradeoffs, failure modes и способ проверки. Не оценивай свободный текст поиском ключевых слов. Не выдавай самооценку за объективный анализ архитектуры.

## Добавление технологии

EF Core + SQLite и Dapper уже поддержаны через разрешённые NuGet dependencies. Для сетевой практики Redis, broker или другого языка потребуется отдельный executor/образ и ограничения. Не имитируй реальную проверку regex-анализом исходника. Задания без исполнения можно сразу добавлять как review с явной маркировкой. Для NuGet добавь фиксированную версию в `trainer/content/packages.json` и поле `packages: ["Microsoft.EntityFrameworkCore.Sqlite"]` у C# задания. В `packages` указываются только имена из manifest. Версии с wildcard/range не допускаются. При первой проверке отдельный доверенный restore-контейнер заполнит volume; код участника получит его read-only и продолжит работать с `--network none`. Rebuild для изменения managed dependencies не нужен. Системные/native prerequisites всё ещё должны быть в образе. Смотри C24–C26 и docs/BANK_UPDATE_20261024.md.

Основной `source` предназначен для документации механизма; дополнительные ссылки задаются через `references: [["название", "https://..."]]` и отображаются в карточке. Не выдавай подборку вопросов за технический стандарт или доказательство частоты вопроса в компании.

Отступы в `starter` практических задач задаются символами табуляции (`\t`), один таб на уровень. В редакторе таб соответствует 4 колонкам. Меняй форматирование одинаково в `tasks.json` и `tasks.en.json`; пробелы внутри строковых литералов и SQL-данных не заменяй. Сохранённые пользовательские решения при обновлении заготовок не переписываются.

Для упражнений на проведение code review (`engine: review`) добавь `review_code` — неизменяемый фрагмент и `review_language` (`csharp` или `sql`). В `starter` задаётся шаблон замечаний кандидата, а не исходник. Фрагмент показывается отдельно с подсветкой; режим AI `review_assessment` оценивает `candidate_review` по коду и рубрике. Примеры: A55–A58. Включи эти поля в AI-контекст при добавлении нового транспорта.
