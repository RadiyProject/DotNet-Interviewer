## Где найти

В **«Теория»** появились отдельные темы **CQRS**, **DDD**, **Clean Architecture**, **«Командная работа»**, **«Процессы и методологии»**. В **«Архитектура и ревью»** — соответствующие категории практики. Для Security, CI/CD, Kubernetes, Git и Architecture используются существующие категории.

Добавлены теги `cqrs`, `ddd`, `clean-architecture`, `teamwork`, `processes` с RU/EN подписями. Они доступны в общих фильтрах и конструкторе; отдельные новые экраны не создавались. В связанных карточках есть переходы между теорией, практикой и ранее существовавшими заданиями.

## Что считается практикой

Практика здесь — конкретный результат в редакторе: исправленный YAML/код, схема зависимостей/контекстов, payload/API, запланированные команды, runbook или письменное решение командного конфликта. У каждой задачи есть условия, осложнения, критерии и содержательный разбор, а не только просьба «рассказать о технологии».

Все A91–A103 — `engine: review`: результаты оцениваются по рубрике самостоятельно или обсуждаются с ассистентом. Git-команды, workflow и manifests — учебные артефакты; они не выполняются в этом репозитории, CI или кластере. Фрагменты A91/A100 намеренно содержат проблемы и не компилируются автоматически. Не выдаём самооценку за функциональную проверку.

Q201–Q224 — одиночный выбор с заданными условиями, объяснением и связанной практикой. Позиции верных ответов распределены по вариантам, а не всегда стоят первыми.

## Смысловые границы

- Security дополняет уже имеющиеся JWT/IDOR/CSRF задачи: фокус нового материала — SSRF, redirects/DNS/connect race и отличие CORS от контроля доступа.
- CI/CD не повторяет только определение OIDC: нужны trust boundaries untrusted PR, происхождение артефакта, одинаковый digest и схема, совместимая со старым кодом.
- Kubernetes: PDB не считается защитой от всех аварий; namespace не заменяет RBAC; peer entries в NetworkPolicy имеют OR, а selectors одного peer — совместные условия. Учитываются plugin/NAT/DNS особенности.
- Git дополняет базовые reset/rebase/revert: отдельно разобраны mainline parent и сохранённая ancestry после revert merge.
- Архитектурные стили рассматриваются на разных осях. CQRS не требует Event Sourcing, брокера или конкретной mediator library. Bounded Context не равен таблице/процессу. Clean Architecture не обеспечивается одними папками или DI container.
- DDD-модель защищает инварианты, но не устраняет гонки persisted copies без concurrency control. Domain/integration events имеют разные границы и совместимость.
- Scrum-вопросы привязаны к **Scrum Guide 2020**, Kanban — к **Kanban Guide May 2025**. Рекомендации упражнения не выдаются за обязательные правила framework. Прогноз, DoD, Sprint Goal и acceptance criteria различаются.
- Командные кейсы требуют фактов, компромиссов, коммуникации и ответственности за действия. Количество коммитов/points не рассматривается как универсальная личная продуктивность. Внешние сообщения никому автоматически не отправляются.

## Порядок подготовки

1. Security и delivery: Q201–Q205 → A91 → A92 → A93.
2. Kubernetes и Git: Q206–Q210 → A94 → A95 → A96.
3. Архитектура: Q211–Q219 → A97 → A100 → A99 → A103 → A98. Сначала границы и инварианты, затем согласованность read models.
4. Процессы и команда: Q220–Q224 → A101 → A102. Пиши короткие артефакты с конкретным владельцем, решением и критерием пересмотра.

Для каждой практики сначала самостоятельное решение, затем разбор. При повторении меняй условие: PR из fork, частичный backfill, другая topology DNS, конфликтующий merge, повтор команды или срочный инцидент. Старайся объяснить не только выбранный механизм, но и границу его гарантии.
